## 二、你的第一个核心任务：读懂自然语言任务书

比赛不会直接告诉 Agent：

```markdown
set_scan_chain -count 4 ...
```

而是可能给类似：

> 设计包含两个时钟域，需要建立 4 条扫描链，各时钟域独立处理，负边沿单元需要适当处理……

你的任务就是把这种自然语言变成 **原子化 DFT 要求** 。

例如你最终应该整理成类似：

| 原始要求         | DFT 含义                      | 需要检查的对象      | 后续配置            |
| ---------------- | ----------------------------- | ------------------- | ------------------- |
| 4 条扫描链       | Internal Scan chain count = 4 | FF 数、clock domain | Scan configuration  |
| 两个时钟域       | 不能简单混链                  | clock / FF          | clock domain policy |
| 需要 Scan Enable | 建立测试控制信号              | port / net          | DFT Signal          |
| Wrapper 某范围   | 指定 Wrapper cell 范围        | I/O / hierarchy     | Wrapper Scan        |

这就是团队文档里说的 **“需求矩阵”** ：

> 原始要求 → 规范化语义 → 设计对象 → 工具配置 → Dofile 位置 → 核验报告。
>
> 03-技术路线与系统拆解

而且这不是附属工作。任务一 60 分核心正确性，本质就在考：

## 四、第三个核心任务：建立 DFT 配置规则

你要逐渐成为全队最清楚下面这些东西的人：

### DFT Signal

例如：

- Scan Clock
- Scan Enable
- Test Reset
- Test Mode
- Scan In
- Scan Out

你需要知道：

> 什么情况下需要配置、对应什么设计对象、错误配置会出现什么后果。

---

### Internal Scan

重点包括：

- Scan cell replacement
- scan chain number
- scan chain length
- clock domain
- scan stitching
- scan ordering
- edge handling

官方材料把任务要求到工具配置的映射明确列成：

**测试时钟 / 复位 / SE → DFT Signal**

**链数 / 链长 / 时钟域 → Internal Scan / Lockup**

**Wrapper 范围 → Wrapper Scan**

**输出要求 → write/report 命令** 。

---

### Lockup

这是你这个角色特别需要搞明白的。

例如：

```markdown
posedge FF → negedge FF
clock domain A → clock domain B
```

什么时候有 shift timing 风险？

什么时候需要 lockup latch / lockup FF？

为什么？

这些以后都会直接影响 Agent 对 Dofile 的配置判断。

---

### Wrapper Scan

至少需要理解：

- 什么是 wrapper cell；
- 为什么 core boundary 需要 wrapper；
- 哪些 port 需要纳入；
- wrapper control；
- wrapper chain；
- Internal Scan 和 Wrapper Scan 的区别与关系。

## 五、第四个核心任务：建立 DRC 诊断知识库

任务二会给一个有问题的 Dofile。

Agent 执行以后可能出现：

```markdown
DRC-xxx
clock uncontrollable
reset uncontrollable
scan enable invalid
...
```

这时候不能做：

> 看见 error → 让 LLM 随便改几行 → 再运行。

你负责建立：

```markdown
DRC
↓
现象
↓
可能原因
↓
需要检查的网表对象
↓
需要查询的手册规则
↓
允许采取的修复
↓
验证方式
```

例如概念上：

```markdown
某 FF 的 asynchronous reset 在 scan mode 不可控制
        ↓
检查 reset cone
        ↓
检查 test mode 下 reset 是否可控
        ↓
判断问题来自 Dofile 配置还是网表结构
        ↓
最小修复
        ↓
重新 DRC
```

这正对应团队文档要求你做的：

> **梳理 DFT Signal、Internal Scan、Wrapper、Lockup 和 DRC 分类；为关键报告字段和 DRC 根因提供可执行验收断言。**

## 六、第五个核心任务：定义“什么叫真的做对了”

这是非常重要的一点。

比赛明确不是：

```markdown
tool exit code == 0
```

就算成功。

工具完全可能：

```markdown
SUCCESS
```

但是：

```markdown
任务要求：4 chains
实际：2 chains
```

一样是错的。

所以你需要定义验收规则。

例如：

```markdown
task_spec
要求 4 条 chain
        ↓
scan_chain.rpt
        ↓
解析 chain_count
        ↓
assert chain_count == 4
```

再比如：

```markdown
任务要求 Wrapper A/B/C
        ↓
wrapper_configuration.rpt
        ↓
检查对象集合
```

团队技术路线明确要求：

> 不把“工具成功退出”当成完成，而是逐条核对需求矩阵，例如链数、链长、时钟域、Wrapper 范围和指定输出。

> 03-技术路线与系统拆解
