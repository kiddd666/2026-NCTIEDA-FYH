# Task2 静态 DFT 规则卡报告

本报告配合 [[../../../docs/DFT与规则学习/案例学习/案例具体分析/03-Task2静态DFT规则卡|Task2 静态 DFT 规则卡]] 使用，帮助刚开始做 DFT 的研究生理解 Agent 怎样根据证据修复 Dofile。

## 1. 概述：Task2 是基于证据的脚本诊断

Task1 主要是按照任务书建立测试结构，Task2 则是在已有脚本上定位并修复配置问题。

每个 Task2 case 都提供了原始 Dofile、官方参考 Dofile 和 `preset_issues.json`。这个 JSON 文件像一张由出题方整理好的故障清单：它记录问题编号、现象、根因、官方允许的修复方向、禁止的绕过方式，以及修复成功以后要观察什么。

五个 case 一共 30 个预置问题。规则卡的目标不是把这30条原文重新抄一遍，而是从中提炼可迁移的判断方法。

## 2. 一张 Task2 规则卡怎样帮助诊断

诊断过程可以固定为四步：先记录现象，再确认配置和连接，之后选择修复，最后用新的报告复查。

- `observable` 是现象：日志报错、DRC 违例、链数不对、端口名不对；
- `recognition` 是分诊方法：怎样把相似症状分开；
- `root_cause` 是诊断结论：为什么会出现这个症状；
- `standard_fix` 是正常治疗；
- `forbidden_fix` 是不能使用的“遮住体检报告”的方法；
- `verification` 是复查指标。

例如“扫描链没有建立”可能来自网表没有加载、扫描时钟写错、scan_enable 没有控制 ICG，也可能只是链数配置不符合任务。表面结果相似，检查入口完全不同。

## 3. 第一类：Dofile 没有正确执行

T2C1 和 T2C2 中有很多属于命令执行层面的故障：

- 没有执行 `load_netlist` 就 `present_design`；
- 把 NAND 单元写成扫描单元映射目标；
- 把 `insert_dft_logic` 放到 DRC 检查之前；
- 使用工具不支持的选项；
- 把不存在的端口名写成扫描时钟；
- 给 clock 类型信号加了只适用于 scan_enable 的选项；
- `-off_state` 写成了工具不接受的数值。

这些问题的共同特点是：后面的 DRC 结果可能只是连锁反应。比如设计根本没有加载成功，后面出现几十条或几百条违例，并不代表网表真的有几百个独立设计错误。

所以第一步永远是检查日志中最早出现的错误，并确认命令是否真正生效。不能看到最后一条 DRC 就直接修改网表。

## 4. 第二类：信号角色和极性错误

扫描时钟、扫描使能和复位，都是“工具如何模拟测试状态”的说明。

把复位端口写成扫描时钟，就像把“刹车踏板”告诉机器是“发动机转速表”；端口也许存在，但角色完全错误。

复位的 `-off_state` 也不能只看端口名字猜。必须沿着网表看信号经过了哪些反相，再判断传到 FF 控制脚时，什么电平表示“复位关闭”。

scan_enable 还有一个常见陷阱：它可能只连接扫描 FF 的 SE，却没有连接 ICG 的测试控制脚。这样扫描 FF 看起来有扫描使能，但门控时钟仍然关闭，移位操作依旧无法传播。

因此卡片要求同时检查：

- `scan_signal` 报告中的类型和极性；
- 真实网表中的连接；
- DRC 中受影响对象的分布；
- 扫描链是否真正建立。

## 5. 第三类：分区、链数和端口契约错误

DRC 全部通过，也可能不满足任务。

例如任务要求4条扫描链，但脚本配置了2条；或者 WB 时钟域应该进入 `wb_partition`，却因为时钟写错落入默认分区；又或者链结构正确，但 SI/SO 端口使用了工具默认名字，不符合任务书要求的 `scan_data_in_%d` 和 `scan_data_out_%d`。

这类问题说明一个重要原则：

> DRC 是结构安全检查，任务契约还包括数量、归属、命名和输出格式。

所以修复后必须同时看 scan configuration、partition、chain、signal 和最终网表，不能只看 DRC 数字。

## 6. 第四类：工具不会自动理解所有时钟结构

T2C3 展示了两个容易混淆的时钟问题。

第一种是多级 ICG 级联。测试仿真每个周期只能让使能传播一级，如果级联深度是3，而初始化周期还是0，下游 FF 的时钟就可能仍然不可控。这时要根据真实级联深度设置初始化周期，不能简单 Ignore DFTR1。

第二种是时钟经过 latch。工具可能看不出 latch 的输出仍然属于主时钟域，因此需要在扫描时钟声明里用 `-associated_internal_clocks` 建立关联。同时，这个时钟传输 latch 本身还可能需要排除出扫描元素。

这两个问题的共同点是：不是“看到时钟错误就换一个端口”，而是要把时钟的真实传播路径告诉工具。

## 7. 第五类：哪些东西可以忽略，哪些不能

规则卡中特别强调 Ignore 和排除范围，是因为它们既可能是合法配置，也可能是逃避问题。

如果任务书明确允许忽略 ICG 内部 latch 的 TIE 类规则，那么配置该 Ignore 是完成任务的一部分。

如果任务明确要求 JTAG TAP 不入扫描链，那么 `set_scan_element false` 是正确的范围声明。

但如果一个功能 FF 本来要求100%覆盖，却把它排除，只为了让 DRC 变成零，那不是修复，而是减少被检查的对象。

判断标准不是“用了 Ignore 就一定错”或“用了 false 就一定错”，而是：当前任务是否明确授权、被处理的对象是否属于授权范围、其他必须清零的规则是否仍然清零。

## 8. 第六类：修复脚本还要交付结果

T2C5 最后说明，Dofile 执行到 `exit` 不等于任务交付完成。

任务还要求导出 post-scan 网表、CTL、SCANDEF、DRC、插链、配置、信号等报告。如果脚本只做了检查，却没有导出这些文件，仍然不满足输出契约。

因此规则卡的成功判据通常分成两部分：一部分是工具状态，例如某类违例消失；另一部分是交付状态，例如指定文件真实存在、命名正确、内容能和最终网表对上。

## 9. 收尾：从“修一行”到“证明修好了”

Task2 规则卡要求形成一个完整习惯：

先找到最早的真实错误，再用任务书和网表确认根因；修复时保持范围最小，不能靠屏蔽日志或删掉对象；最后用报告、网表和日志证明修复结果。

预置问题是学习材料，不是未来 Hidden case 的固定答案。未来遇到不同端口、不同层级和不同数量时，要复用诊断方法，而不是复制案例参数。
