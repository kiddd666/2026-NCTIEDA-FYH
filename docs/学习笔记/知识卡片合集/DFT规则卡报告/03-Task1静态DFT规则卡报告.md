# Task1 静态 DFT 规则卡报告

本报告配合 [[../../../docs/DFT与规则学习/案例学习/案例具体分析/02-Task1静态DFT规则卡|Task1 静态 DFT 规则卡]] 使用，帮助刚开始做 DFT 的研究生理解：任务书如何变成一组可以执行、检查和复核的规则。

## 1. 概述：Task1 不是“把所有东西都插上扫描链”

先纠正一个很常见的理解。Scan Insertion 不是看到一个芯片，就把所有寄存器和所有时钟简单串起来。

有些任务只要求把普通寄存器换成可扫描寄存器；有些任务要求真正建立扫描链；有些任务还要求处理黑盒、时钟门控、wrapper 或已有的扫描段。

Task1 的六个 case 正好展示了这六种边界。因此这份规则卡没有把六个案例强行写成同一个模板，而是先确认每个 case 的任务终点，再提炼规则。

## 2. 两类东西：配置和证据

每张卡都把“应该怎样配置”和“怎样证明配置生效”分开。

配置是 Dofile 中的动作，例如设置扫描时钟、指定 DFF 到 SFF 的映射、定义扫描分区、配置 wrapper 或导出报告。

证据是动作完成后的结果，例如配置报告、DRC 报告、扫描链报告、最终网表和完整日志。

这就像装修房子：施工图不是竣工验收，工具命令不是最终证明。必须检查实际墙体、线路和验收记录。

## 3. T1C1 和 T1C4：前置处理

T1C1 和 T1C4 不要求建扫描链。它们主要做三步：

1. 把符合条件的时钟门控测试端接到扫描控制信号；
2. 把普通 DFF 替换为功能对应的 SFF；
3. 把明确不属于扫描时钟域的既有 SFF 回替为普通 DFF。

所以这两个 case 的关键证据是三个阶段网表：连接后的网表、替换后的网表、回替后的最终网表。不能拿“链数为零”当作失败，因为任务本来就没有要求建链。

T1C4 还特别要求 ICG 数量、CLK/EN 连接和触发器总数保持不变。因此它是一个结构守恒检查：只改变被允许改变的测试连接和单元类型，不能改动原始功能结构。

## 4. T1C2：把芯片按功能分成不同检查区域

T1C2 的核心是按功能区域划分扫描分区。不同区域虽然都包含寄存器，但它们的时钟、扫描使能和链数要求可能不同，因此不能把所有对象放进同一条链。

这个 case 把 AC97 设计拆成 FIFO、串行接口、寄存器、Wishbone 和控制等七个显式分区。每个分区有自己的链数、最大链长和 scan_enable。

Dofile 中要先配置全局时钟、复位、lockup 和 SI/SO 命名，再使用 `add_scan_partition` 指定对象，之后通过 `set_current_scan_partition` 在当前分区上下文中配置链数和扫描使能。

最终不能只看 DRC。还要看：

- 分区报告中的实例归属；
- 扫描链报告中的链数和链长；
- 扫描信号报告中的时钟、复位和 scan_enable；
- 配置报告中的 lockup、替换和端口命名；
- 插链后的网表、CTL 和 SCANDEF。

## 5. T1C3：看不见的黑盒也必须接入整体测试结构

T1C3 集成了 AES 黑盒。黑盒只暴露接口，内部电路不可见。

因此 Dofile 不能只加载顶层网表，还要加载黑盒的 Liberty 模型和 CTL 文件。CTL 文件告诉工具：这个黑盒内部已经有哪些扫描段、扫描输入、扫描输出和扫描使能。

这个 case 还要求 dedicated wrapper、wrapper/unwrapper 链数量，以及某个层级的大部分扫描单元排除、其中 `mintthresh*` 子集保留。

报告证明要看四件事：

1. CTL 扫描段是否被识别；
2. wrapper 配置是否启用且数量正确；
3. 链报告是否分别满足 wrapper 和 unwrapper 数量；
4. 导出的顶层 CTL 是否按实例路径引用黑盒扫描段。

如果不可拆的 CTL 段导致 wrapper 链超过最大长度，任务书对这种特定情况给了例外。这个例外不能扩展成“所有超长链都可以忽略”。

## 6. T1C5：先告诉工具内部时钟从哪里来

T1C5 是大型多时钟设计。可以采用一个简化模型：顶层端口是已知时钟源，内部经过门控单元形成多个时钟支路；工具若看不出这些支路的测试状态，就需要在 Dofile 中显式声明。

有些内部时钟输入是悬空的门控时钟输出。任务书要求把这些点声明为 pseudo PI，让工具知道它们是需要独立分析的测试时钟来源。

此外还要告诉工具：

- 哪些顶层端口是扫描时钟；
- APB 时钟经过哪个内部时钟结构传播；
- 扫描模式应锁为1；
- MBIST模式应锁为0；
- 哪些信号控制扫描 FF，哪些信号控制 ICG；
- 四个复位端口的关闭电平是什么。

最后的证明链是：扫描信号报告证明环境配置正确，DRC 报告证明时钟和复位可控，扫描链报告证明所有可扫描 FF 入链且链长不超过500，最终网表、CTL 和 SCANDEF 证明插入结果落地。

## 7. T1C6：已有的长扫描段不能被随意拆开

T1C6 中的长移位寄存器已经有自己的扫描入口和出口，任务要求把它作为完整 segment 保留下来，而不是为了满足链长限制把 segment 拆散。

这个 case 还要求 wrapper：`key1` 不参与扫描，`key2` 使用用户提供的 dedicated cell，`key3` 使用 shared wrapper，其余端口遵循全局策略。

Dofile 中要先配置时钟、scan_enable、wrapper 控制信号和内部链参数；然后注册自定义 dedicated wrapper cell；再按真实网表端点用 `set_scan_segment` 注册所有长段。

最后需要同时查看内部链和 wrapper 链。只证明内部链不断裂是不够的，还要证明 wrapper 风格、专用 cell 接口、shift/capture 控制、链长和输出文件都正确。

## 8. 为什么这些卡片没有编造故障

Task1 的 Public 材料主要提供任务书和 golden.dofile，没有像 Task2 那样的官方 `preset_issues.json` 和运行日志。

因此卡片中的 `REQ-01`、`REQ-02` 等是“要求检查编号”，不是官方报告的故障编号。

卡片里的 `observable` 表示“运行后应该观察什么”，不是“Public 已经观察到了什么”；`root_cause` 只有在真实日志、报告和网表支持时才能写成确定结论。

这也是静态规则学习和真实验收的区别：规则卡教 Agent 应该检查哪里，真实工具产物才决定这一次运行是否通过。

## 9. 收尾

Task1 规则卡最终想教会 Agent 的不是背命令，而是先问三个问题：

“这个 case 的终点是什么？”

“哪些结构或对象允许改变？”

“哪一份最终产物能证明改变范围恰好正确？”

只要这三个问题答清楚，Dofile 才不会变成盲目复制，报告也不会只剩一句“DRC pass”。
