# Public 材料指纹报告

本报告配合 [[../../../docs/DFT与规则学习/案例学习/案例具体分析/04-Public材料指纹.json|Public 材料指纹清单]] 使用。

## 1. 概述：为什么还要给材料做“指纹”

复核一份合同或实验材料时，不能只记录“看过文件”，还需要知道是哪一版、文件有没有被替换、页数是否一致。

Public 材料指纹清单做的就是类似的事情。它给每个材料记录路径、字节数、行数和 SHA-256 摘要。SHA-256 可以先理解成文件的“数字指纹”：文件内容哪怕改了一个字符，指纹通常也会变化。

这份清单不是 DFT 工具的输出，也不是官方提交格式。它是仓库内部为了保证可追溯而建立的来源登记。

## 2. 这份 JSON 里面有什么

清单分成两部分。

第一部分是 case 摘要：每个 case 的 wall time、任务书中声明的输入是否存在，以及任务二有没有官方问题编号。

第二部分是文件清单：Public 目录下材料的相对路径、大小、行数、SHA-256 和材料角色。

角色是为了帮助阅读者理解文件用途，例如：

- `task_spec.md` 是任务契约；
- `limitations.md` 是运行限制；
- `golden.dofile` 是参考脚本；
- `original.dofile` 是需要修复的脚本；
- `preset_issues.json` 是官方预置问题说明。

这些角色不会改变原文件内容，只是给它们加了一张目录卡。

## 3. SHA-256 怎样帮助核对材料

可以把 SHA-256 理解为文件内容生成的数字指纹。

文件名可能相同，甚至文件大小也可能相同，但内容不一定相同。拿到另一份材料时，可以重新计算它的 SHA-256，再和清单比较。如果不一致，就需要回头确认：是材料版本变化、文件传输损坏，还是本地文件被修改过。

这对于 DFT 学习很重要，因为规则卡中的结论必须能够回到具体 Public 材料。否则过了一段时间，可能无法确认当时引用的是哪一版任务书。

## 4. 为什么还记录行数和字节数

SHA-256 适合判断“内容是否一致”，但不方便人直接阅读。字节数和行数是更直观的快速检查：

- 字节数可以发现文件是否明显变小或变大；
- 行数可以帮助核对规则卡中引用的行号；
- 路径说明材料属于哪个 task 和 case。

它们不是语义证明。例如行数相同，并不代表每一行内容都正确；所以最终仍以 SHA-256 和原文为准。

## 5. 为什么大网表要特别说明

Public 中有两份大型网表被 Git 排除，但在本机材料目录中存在。它们的大小很大，不适合按普通 Git 文件处理。

因此清单把“Git 提交中的材料”和“本机存在但被排除的输入网表”区分开。这样做是为了避免两种错误理解：

1. 看到 Git 没列出文件，就误以为 case 输入缺失；
2. 看到本机有文件，就误以为它一定属于当前 Git 提交。

清单能证明这些文件在登记时位于指定路径、具有指定大小和指纹；它不能证明 EDA 工具已经成功加载或运行通过。

## 6. 指纹清单不能证明什么

这部分非常重要。材料指纹只能证明“引用的是哪份材料”，不能证明：

- golden.dofile 一定可以运行；
- DRC 一定为零；
- 扫描链一定建立成功；
- 最终网表一定与原设计功能等价；
- 某个案例已经完成真实验收。

这些结论必须由真实工具日志、配置报告、DRC 报告、扫描链报告和最终网表来证明。

换句话说，指纹解决的是“证据从哪里来”，规则卡和运行报告解决的是“证据说明了什么”。

## 7. 收尾

这份 JSON 像实验记录本的封面和借阅登记。它用于回答“引用的是哪份材料”，也让其他人能够按路径和指纹复核同一份材料。

它不替代工程验证，但它是工程验证的起点：如果输入材料都没有被准确登记，后面的规则判断和运行结论就很难追溯。
