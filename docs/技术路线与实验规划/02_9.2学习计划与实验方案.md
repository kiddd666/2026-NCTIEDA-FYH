# 9.2—9.5 学习计划与前置实验方案

**一句话结论：**未来四天不再大面积补理论，而是用约 70% 的时间完成一个“可复现、可诊断、可取证”的开源 Scan Insertion 前置闭环；四天结束时，应能把模拟任务要求映射为网表分析结果、Scan 配置、实验运行、报告断言和 EQY 证据，从而在 Public Case 与广立微手册到位后只替换工具专用层。

本文只确定学习与实验方案。待确认后，再在 `FYH/experiments` 中创建目录、配置环境并执行；当前不得凭经验编写或宣称支持任何广立微专用 Dofile 命令、参数或 DFTR 规则。

- 已学习《VLSI Test Principles and Architectures》Chapter 1 与 2.1～2.7，已经接触故障模型、可测性、Scan 基础、时钟/复位与 DRC 原理；

- 本机已有可用的 OSS CAD Suite、Yosys、Icarus Verilog、VVP 和 GTKWave 环境记录；
- 2026-09-02 下午计划学习英文教材 10.4.2～10.4.5，主题为 IEEE 1500 Wrapper、Wrapper 组件、指令和 CTL。

### 1.2 当前最值得补的能力

结合现有路线与缺口报告，当前优先级是：

1. 把已有零散实验整理成一条可重复执行、保留日志和明确 PASS/FAIL 的流程；
2. 从“能看 Verilog”升级到“能联合门级网表与 Liberty 输出结构化设计摘要”；
3. 从“能写 Scan Chain”升级到“能验证功能模式、Shift/Capture、链数/链长和故障现象”；

5. 跑通 EQY 的 PASS、真实 FAIL、配置 ERROR 三类结果；
6. 用模拟赛题输入和输出目录完成一次无人提示的闭环演练。

暂不优先投入：复杂 ATPG、完整 JTAG、RAM/MBIST、复杂 Multi-Agent 框架、广立微私有命令猜测，以及没有真实手册依据的 DFTR 编号背诵。

- 遇到失败先分类为环境/配置、实验模型、设计结构或真实功能错误，再决定修复方向。

## 3. 第一天：Wrapper 学习与旧实验基线化（9 月 2 日）

### 3.1 学习内容

阅读英文教材 10.4.2～10.4.5，但只围绕比赛会用到的六个问题做笔记：

1. Wrapper 与 Internal Scan 分别控制/观察什么位置；
2. Wrapper Cell、WBR、WIR、WBY、TAM 的角色和连接关系；
3. `INTEST`、`EXTEST`、`BYPASS` 等指令改变了哪条数据路径；
4. 输入、输出、双向端口的 Wrapper Cell 行为有什么区别；
5. CTL 描述什么信息，它不能替代什么；
6. 教材中的 IEEE 1500 原理，哪些仍需等待广立微手册确认。

产出一张矩阵：

| 概念 | 所在位置 | 控制/观察对象 | 典型模式 | 未来应查报告 | 当前证据等级 |
| --- | --- | --- | --- | --- | --- |
| Internal Scan Cell | Core 内部 | 内部状态 | Shift/Capture | Scan Chain/Cell 报告 | 教材原理 |
| Wrapper Cell | Core 边界 | Core 端口与外部互连 | INTEST/EXTEST | Wrapper 报告 | 教材原理，工具字段待确认 |

### 3.2 实验 E0：已有实验回归与证据基线

**目的：**把 `D:\research\Scan-Insertion` 中“曾经跑过”的实验转化为后续四天可依赖的基线。

执行内容：

1. 记录 Yosys、Icarus Verilog、VVP、GTKWave、Python 的版本和实际路径；
2. 复跑普通 DFF、Scan DFF、4-bit Scan Chain；
3. 将 4-bit Scan Chain Testbench 补成自检形式，覆盖：
   - Reset；
   - `scan_enable=0` 的功能捕获；
   - `scan_enable=1` 的 Shift-In；
   - Capture；
   - Shift-Out 与期望序列比较；
4. 保存编译命令、仿真日志、VCD 和一张关键波形截图；
5. 给每个实验写一行结论：输入、预期、实际、PASS/FAIL、若失败则根因。

**通过标准：**重复执行得到相同结果；4-bit Scan Chain 的正确性由 Testbench 自动判断，而不是只凭 GTKWave 观察。

**故障注入：**把一个级间连接故意断开或交换，确认 Testbench 能稳定报 `FAIL`。这一步验证的是“验收器能抓错”，不是只验证正确设计。

### 3.3 第一天结束时应能回答

- 为什么 Wrapper Scan 不能替代 Internal Scan？
- 现有 4-bit Scan Chain 的 Shift-In、Capture、Shift-Out 分别发生在哪些周期？
- 如果 Scan Chain 接错一位，现有验证为什么一定能发现？

## 4. 第二天：门级网表与 Liberty 联合分析（9 月 3 日）

### 4.1 即用即学内容

只学习支撑实验的内容：

- 结构化门级 Verilog 的实例、端口连接、层次与转义标识符；
- Yosys `read_verilog`、`hierarchy`、`proc`、`flatten`、`stat`、`write_json` 的作用；
- Liberty 中 `cell`、`pin`、`direction`、`function`、`ff`、`latch`、clock/control pin；
- `dfflibmap` 与 `abc -liberty` 在 RTL 到标准单元网表流程中的位置；
- `read_liberty -lib` 只导入库信息/黑盒的边界，以及仿真时为何还需要 Verilog cell model。

### 4.2 实验 E1：Yosys 官方 cell library mapping 最小案例

使用 Yosys 官方 counter/`mycells.lib` 示例或等价的极小设计，完成：

```text
RTL
→ Yosys 综合
→ dfflibmap / abc -liberty
→ 门级 Verilog + JSON + 综合日志
→ Icarus 功能回归
```

需要记录每一步前后的 cell 类型变化，并解释 `techmap`、`dfflibmap` 和 `abc -liberty` 分别解决什么问题。

**通过标准：**生成的网表仅引用预期库单元；综合前后功能回归通过；若删除一个 cell model，能够识别这是模型/配置错误而不是设计功能错误。

### 4.3 实验 E2：`s27` 的结构化 `design_summary`

在现有 `s27` 分析基础上，形成一个最小分析器或可复用脚本，输出：

```json
{
  "top_module": "",
  "ports": [],
  "cell_type_counts": {},
  "sequential_cells": [],
  "clock_candidates": [],
  "reset_set_candidates": [],
  "clock_domains": [],
  "latches": [],
  "ram_or_blackboxes": [],
  "library_missing_cells": [],
  "warnings": []
}
```

分析器至少完成：

1. 从 Yosys JSON 读取 module、port、cell、connection；
2. 识别时序单元候选及其 D/Q/clock/reset 连接；
3. 从顶层输入追踪 clock/reset 到时序 pin 的直接连接；
4. 对照 Liberty 检查 cell 是否存在、关键 pin 方向是否一致；
5. 对无法判断的对象输出 `unknown`/warning，不凭实例名强行推断。

**故障注入：**分别制造一个不存在的 cell type、一个错误 pin 名或一个缺失 cell model，验证异常清单能指出具体对象。

**通过标准：**从结构化输出可以回答顶层、端口、时序单元数量、clock/reset 候选及库缺失；结论能回指到具体实例和网络。

## 5. 第三天：手工 Scan Insertion、链平衡与 Lockup（9 月 4 日）

### 5.1 即用即学内容

- Scan MUX、Scan Cell、Shift/Capture、Scan In/Out、Scan Enable；
- Full Scan 与 Partial Scan 的差别；
- chain count、最大链长、链平衡与 shift cycle 的关系；
- clock domain、正/负边沿、skew、hold 风险和 Lockup 的作用；
- 零延迟 RTL 仿真只能展示事件顺序，不能证明真实硅上的 hold timing。

### 5.2 实验 E3：小型 DUT 的手工 Scan Insertion

选择一个含 6～8 个寄存器、少量组合逻辑和复位的小型 DUT，保留独立的 Pre-scan 基线，手工完成：

1. 普通 DFF 替换为自定义 Scan DFF；
2. 先连接为 1 条 Scan Chain，再连接为 2 条尽量平衡的 Scan Chain；
3. 编写自检 Testbench，分别验证：
   - `scan_enable=0` 时功能行为与 Pre-scan 一致；
   - Reset 后状态符合预期；
   - Shift-In 的位序正确；
   - Capture 得到预期响应；
   - Shift-Out 的序列、链首和链尾正确；
4. 统计 1 链和 2 链的最长链长、加载/卸载周期和端口数量；
5. 输出一份模拟 `scan_chain_report.json`，字段至少包括 chain name、length、cells、scan in/out、clock domain 和 edge。

**故障注入：**覆盖 SE 极性错误、链断开、链顺序错误、漏掉一个寄存器、任务要求 2 链但实际只有 1 链。

**通过标准：**功能模式回归和 Scan 模式回归均通过；报告断言能发现链数、链长、漏单元和连接错误。

### 5.3 实验 E4：多时钟/混合边沿与 Lockup 对照

建立四个最小变体：

| 变体 | 结构 | 要观察的现象 | 处理/结论 |
| --- | --- | --- | --- |
| A | 同时钟、同边沿 | 基线移位 | 普通串接 |
| B | 两个 clock、同边沿且人为加入 skew | 潜在 hold 窗口 | 比较无/有 Lockup |
| C | `posedge` → `negedge` | 半周期与边沿顺序 | 记录 launch/capture 时间 |
| D | gated clock | Shift 时钟可能被关断 | 加 test enable/override 对照 |

至少实现一个 Lockup Latch 或 Lockup FF 的行为模型，并比较插入前后波形。若 OpenSTA 环境可在 30 分钟内就绪，再增加 `report_checks -path_delay min`；若安装阻塞，则保留为后续扩展，不能让它拖垮主线。

**通过标准：**能根据波形指出数据在哪个边沿发射、在哪个边沿被下一级接收、Lockup 提供了什么隔离；不得把零延迟仿真结论表述为真实 hold 已被签核。

## 6. 第四天：EQY 三态与模拟赛题闭环（9 月 5 日）

### 6.1 实验 E5：EQY 的 PASS、FAIL、ERROR 三类结果

先运行 EQY 官方 simple/counter 示例，再自建三个最小案例：

| 案例 | 修改方式 | 预期结果 | 必须检查的证据 |
| --- | --- | --- | --- |
| PASS | 只改变结构，不改变功能 | EQY PASS | `PASS`、日志、两侧 top 与输入文件 |
| FAIL | 改变一个条件、常量或状态更新 | 真实不等价 | `FAIL`、失败 partition/counterexample |
| ERROR | 错误 top、缺 cell model 或路径错误 | 配置/建模错误 | gold/gate/combine 日志，不能误报为功能不等价 |

建议再做一个贴近比赛的 PASS 样例：对 Pre-scan 网表工作副本做最小等价重写，先证明 EQY PASS，再允许进入后续 Scan 实验。

**通过标准：**只看退出码之外，还能自动输出分类：`equivalent`、`non_equivalent`、`configuration_error`、`unknown`，并附真实证据路径。

### 6.2 实验 E6：无广立微工具的模拟赛题闭环

创建一个合成 case，不写任何虚构广立微命令：

```text
mock_case/input/
├── pre_scan.v
├── stdcells.lib
├── cell_models.v
├── task_spec.md
└── limitations.md
```

模拟 `task_spec.md` 可包含：

- 指定 top；
- 指定 Scan Clock、Reset、Scan Enable；
- 要求 2 条 Scan Chain；
- 要求各链长度差不超过 1；
- 指定是否允许混合 clock domain；
- 要求输出 Post-scan 网表、链报告和决策记录。

闭环步骤：

```text
读取 task_spec
→ 生成结构化 expected_dft.json
→ 分析 pre_scan.v + stdcells.lib
→ 生成 design_summary.json
→ 执行手工/教学 Scan 变换
→ 运行功能与 Scan Testbench
→ 生成模拟 scan_chain_report.json
→ 按 expected_dft.json 做断言
→ 若修改 Pre-scan 工作副本则先跑 EQY
→ 输出 runs/R1、final_results 和 decision_log.json
```

至少人为设置两个问题并闭环：

1. **DFT 配置问题：**任务要求 2 链，第一次只生成 1 链；
2. **结构/连接问题：**一条链漏接一个寄存器或 Scan Enable 极性错误。

每个问题记录：

```text
found → diagnosis → fix → verify
```

**通过标准：**全流程无需中途人工编辑结果；每条任务要求都有预期值、实际值和证据路径；`final_run` 指向真实成功运行；失败的 R1 仍被保留，R2 修复后通过。

## 9. Public Case 与工具手册到位后的迁移方式

届时不推倒重来，而是按下面的替换关系升级：

| 当前前置实验资产 | 到位后替换/扩展 | 保留不变的能力 |
| --- | --- | --- |

| 自建 EQY 样例 | 官方 LEC 脚本与真实模型 | PASS/FAIL/ERROR 分类与证据门禁 |

拿到材料后的第一动作应是建立“手册命令/规则—真实日志—Public Case 对象—报告字段”的校准表，而不是立即让模型生成完整 Dofile。

## 10. 学习图谱定位

本计划按“工作工程师入门深度”组织，四天重点节点如下：

- 正在推进：门级 Verilog、网表/Liberty 联合分析、DFT/可测性、Internal Scan、Wrapper/CTL；
- 本轮重点补齐：多时钟/Lockup、Dofile/报告验收、EQY、比赛闭环；
- 暂缓：完整 ATPG、JTAG/Boundary Scan、RAM/MBIST 和复杂 Agent 框架。

四天结束后仍不直接把任一节点标记为“已掌握”；需用迁移题或模拟 case 的实际结果再判断。
