# 任务一

任务一的完整闭环是：

> 读取任务说明书 → 分析网表和标准单元库 → 查阅工具手册 → 生成 Dofile → 调用 Scan Insertion 工具 → 检查 DRC/扫描链/Wrapper 报告 → 必要时修改 Dofile 并重跑 → 输出最终网表、报告和审计记录。

## 1. 任务一的输入及含义

每个 case 的输入如下。

| 输入               | 含义                                                                                                      | 举例                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `pre_scan.v`     | 插入 Scan 之前的**门级网表**，是待处理的原始设计。Agent 需要从中识别顶层模块、时钟、复位、DFF/DLATCH、RAM、端口和时钟域。                             | `top` 为 `soc_top`，包含 `clk_a`、`clk_b`、`rst_n`，以及 128 个 DFF。                          |
| `stdcells.lib`   | **Liberty 标准单元库**，描述单元名称、引脚、功能和时序等信息，供工具识别普通触发器、Scan 触发器、Lockup Cell、Wrapper Cell 等。                    | 普通 `DFF_X1` 的引脚可能是 `D/Q/CK/RN`，Scan 单元还需要 `SI/SE` 等引脚。                              |
| `task_spec.md`   | **自然语言插链任务说明书**，是本 case 的“需求合同”。描述顶层设计、测试时钟/复位、`Scan Enable`、链数量或长度、时钟域、边沿、Lockup、Wrapper 范围、控制信号和输出文件。 | “使用 `scan_en` 作为 Scan Enable，建立 8 条尽量均衡的链，跨时钟域插入 Lockup，对 `io_*` 端口做 Wrapper Scan。” |
| `limitations.md` | **运行约束**，包括 Agent 总运行时间和 Scan Insertion 工具最多调用次数，用于控制重试和迭代策略。                                           | 总时间 300 秒，工具最多调用 5 次。                                                               |
| `golden.dofile`  | **正确 Dofile**。只在 Public case 提供，用于学习、调试和对照；Hidden case 不提供。                                             | 可用来验证命令顺序和配置语义，但不能依赖它解决 Hidden case。                                                |
|                  |                                                                                                         |                                                                                     |

此外，主办方统一提供：

- 广立微 Scan Insertion 工具和 License；
- 工具用户手册 PDF。

Public case 的目录大致是：

```
public_case_1/input/
├── netlist/pre_scan.v
├── lib/stdcells.lib
├── task_spec.md
├── limitations.md
└── golden.dofile
```

Hidden case 没有 `golden.dofile`。

## 2. 任务要求需要哪些具体步骤

### 步骤 1：解析任务说明书

将自然语言转换为结构化约束，例如：

```
top_design: soc_top
scan_clock: clk_a, rising
scan_reset: rst_n, active_low
scan_enable: scan_en
internal_chain_count: 8
chain_balance: 尽量均衡
clock_domain_crossing: 使用 lockup
wrapper_scope: io_* 端口
outputs: post_scan.v, design.ctl, design.scandef, reports/*
```

重点是不能遗漏数量、极性、边沿、时钟域和 Wrapper 范围等要求。

### 步骤 2：分析 Pre-scan 网表

确认：

- 顶层模块名称；
- 输入、输出和测试相关端口；
- 时钟、复位、置位信号；
- 可参与扫描的 DFF、Latch 等时序单元；
- 不同的时钟域和时钟边沿；
- 是否存在时钟门控、常量连接或特殊结构。

任务一规定 case 中网表不存在问题，因此不能修改网表。

### 步骤 3：检索并理解工具手册

根据工具手册确认：

- 读入网表和 Liberty 的命令；
- DFT Signal 的配置方式；
- Internal Scan 和 Wrapper Scan 的配置方式；
- Scan Chain、Lockup、时钟域和边沿参数；
- DRC、Scan Chain 预生成和最终插入命令；
- CTL、SCANDEF 及各类报告的生成命令。

命令名称和参数必须以实际工具版本手册为准。

### 步骤 4：生成 Dofile

Dofile 至少应完成以下逻辑：

1. 初始化工具；
2. 加载 `stdcells.lib`；
3. 加载 `pre_scan.v` 并设置顶层设计；
4. 配置 Scan Clock、Reset、Scan Enable 等 DFT Signal；
5. 配置 Internal Scan；
6. 配置 Wrapper Scan；
7. 配置时钟域、边沿和 Lockup；
8. 执行 DRC；
9. 预生成 Scan Chain；
10. 执行 Scan Insertion；
11. 写出 Post-scan 网表、CTL、SCANDEF 和报告。

### 步骤 5：调用工具并保存每一轮结果

每次工具调用都作为独立轮次，例如 `R1`、`R2`：

```
output/runs/R1/
├── R1.log
├── deliverables/
└── reports/
```

必须保存完整日志，而不是只保存最后一次运行结果。

### 步骤 6：检查执行结果

检查：

- 工具是否正常结束；
- DRC 是否通过；
- Scan Chain 数量和长度是否符合任务书；
- 时钟域、边沿和 Lockup 是否正确；
- Wrapper 配置和实现是否正确；
- 参与扫描的时序单元和目标端口是否完整；
- 输出文件是否生成。

### 步骤 7：自主修复并重跑

如果发现命令或配置错误：

- 只能修改 Dofile 或 DFT 配置；
- 不能修改任务一的 Pre-scan 网表；
- 修改后必须重新执行完整流程；
- 不能只绕过错误或屏蔽报告。

例如：

```
R1 报告：Scan Chain 数量为 4
任务要求：Scan Chain 数量为 8
修复：修改 Dofile 中的链数量参数
R2：重新执行 DRC、建链和插链
```

### 步骤 8：确认最终轮次并归档

选择真正满足任务要求的最后一轮，将其复制到 `final_results/`，并生成 `decision_log.json`。

## 3. 输出分别如何得到

| 输出                                        | 如何得到                                                       |
| ----------------------------------------- | ---------------------------------------------------------- |
| 最终 Dofile                                 | Agent 根据任务书、网表、Liberty 和工具手册生成，并经过多轮修正后得到。应是最终成功运行实际使用的脚本。 |

| DRC 报告                                    | 执行 DRC 检查命令后保存，例如工具的 `examine_scan_drc` 结果。                |
| Scan Signal 报告                            | 工具完成 DFT Signal 配置后生成。                                     |
| Scan Element 报告                           | 工具识别和替换的扫描单元清单。                                            |
| Scan Configuration 报告                     | 工具实际生效的 Scan 配置。                                           |

```
├── runs/

│   │   ├── R1.log
│   │   ├── deliverables/
│   │   └── reports/
│   └── R2/

    ├── final.log
    ├── deliverables/
    │   ├── final.dofile
    │   ├── design.ctl
    │   ├── design.scandef
    │   └── post_scan.v
    └── reports/
```

`decision_log.json` 中的 `final_run` 必须指向实际采用的轮次；`requirement_mapping` 应把任务书要求对应到 `final.dofile` 的具体配置位置。任务一若一次运行成功，`issue_resolutions` 可以为空数组。

需要特别注意：评分比较的是 Dofile 的最终配置语义和工具实际结果，不要求文本形式与 `golden.dofile` 逐行一致；只要最终效果等价并满足任务要求即可。

任务二不是从零编写 Dofile，而是从一份“有问题的 `Original Dofile`”开始，经过：

> 基线执行 → 发现问题 → 判断问题类型 → 定位根因 → 修改 Dofile/DFT 配置/网表 → 重新执行完整流程 → 验证问题已消除 → 输出最终结果。

## 2. 三类问题及具体处理步骤

### 2.1 Dofile 执行问题

这类问题导致工具报错退出，或者无法进入后续阶段，常见原因包括：

- 命令名、参数名或参数值错误；
- 文件路径、顶层设计名、对象引用错误；
- 网表或 Liberty 没有正确加载；
- 命令顺序错误或缺少前置步骤。

处理流程：

1. 执行 `original.dofile`，保存完整日志。
2. 根据错误行定位具体命令或参数。
3. 对照工具手册检查语法、参数约束和执行顺序。
4. 修改 Dofile。
5. 重新执行完整 Scan Insertion 流程。
6. 确认工具能够继续运行，并且没有引入新错误。

文档中的示例是：

```
日志：unknown argument '-lenght'
定位：set_scan_chain 命令参数
修复：-lenght 改为 -length
验证：工具继续执行并完成 add_scan_chains
```

### 2.2 DRC 问题

执行 `examine_scan_drc` 后可能发现设计规则违规，例如：

- DFF、DLATCH、RAM 的时钟、复位或置位在测试模式下不可控；
- 时钟不能正常开启或完成捕获；
- 时钟网络错误连接到数据、时钟、置位或复位引脚；
- LS/TE 结构影响数据捕获或时钟路径；
- 常量时序单元或锁存器连接存在问题。

处理流程：

1. 读取 DRC 报告，记录规则编号和违规对象。
2. 分析违规对象在 Pre-scan 网表中的实际连接。
3. 判断根因属于：
    - Dofile/DFT 约束配置错误；或
    - 网表结构本身导致测试模式不可控。
4. 配置类问题：修改 Dofile 或 DFT 约束。
5. 网表类问题：修改 Pre-scan 网表，并保证与原始网表功能等价。
6. 生成网表差异文件和 LEC 报告。
7. 重新执行完整流程，确认 DRC 消除。

不能仅通过降低 DRC 等级、设置 `Ignore`、排除对象或屏蔽报告来“消除”问题。

文档示例：

```
现象：DFTR1，clk_b 在测试模式下不可控
定位：clk_b 上的门控实例 U_gate_clkb
修复：增加由 scan_en 控制的测试旁路
验证：LEC 通过，DRC violations = 0
```

### 2.3 DFT 配置不符合任务要求

这类问题的特点是：Dofile 可以执行，甚至 DRC 也能通过，但最终配置或扫描结构不符合 `task_spec.md`，例如：

- Scan Clock、Reset、Scan Enable 或 Wrapper 控制信号错误；
- Scan Chain/Wrapper Chain 数量、长度、时钟域、边沿或 Lockup 错误；
- Internal Clock、Clock-Gating、Wrapper Cell 类型或端口范围不合理；
- 应扫描的时序单元或目标端口没有被纳入；
- 扫描端口和控制信号连接错误。

处理流程：

1. 读取 Scan Configuration、Scan Chain、Wrapper 报告。
2. 检查 Post-scan 网表中的实际结构。
3. 将报告结果与任务说明书逐项比较。
4. 定位具体命令、参数、时钟、端口或单元。
5. 修改 Dofile 或 DFT 配置。
6. 重新执行完整流程。
7. 确认报告和 Post-scan 网表均满足任务要求。

文档示例：

```
任务要求：8 条 Scan Chain
实际报告：Total scan chains: 4
修复：将 Dofile 中的链数量由 4 改为 8
验证：重新运行后报告为 Total scan chains: 8
```

## 3. 任务二的完整执行流程

### 第 1 步：保留原始输入

不能直接覆盖 `original.dofile` 或原始 `pre_scan.v`。每次修改都应产生新版本，方便比较和审计。

### 第 2 步：执行基线版本

第一次运行记为 `R1`，保存：

```
runs/R1/R1.log
runs/R1/deliverables/R1.dofile
runs/R1/reports/*
```

### 第 3 步：识别和分类问题

根据日志、DRC 报告、Scan Chain 报告、Wrapper 报告和 Post-scan 网表，判断属于哪一类问题。

### 第 4 步：定位根因

不能只复述日志中的报错，要明确指出：

- 哪个命令或参数；
- 哪个端口、时钟或实例；
- 哪段网表连接；
- 为什么导致当前现象。

### 第 5 步：执行修复

每次修复都要记录：

- 修改动作；
- 修改后的文件；
- 与上一轮的 diff；
- 如果修改网表，对应的 LEC 报告。

### 第 6 步：完整重跑

修复后不能只重新执行出错的单条命令，而应重新执行完整 Scan Insertion 流程，生成新的网表和报告。

### 第 7 步：循环验证

直到：

- Dofile 正常执行；
- DRC 通过；
- Scan/Wrapper 配置满足任务书；
- 没有新增错误；
- 所有预设问题均形成“发现—诊断—修复—验证”闭环；
- 没有超过时间和工具调用次数限制。

### 第 8 步：确定最终轮次

例如：

```
R1：Dofile 参数错误
R2：Dofile 修复后暴露 DFTR1
R3：网表修复后 DRC 通过，但链数错误
R4：链数修复，最终通过
```

此时 `final_run` 应设置为 `R4`，并将 R4 的结果复制到 `final_results/`。

## 5. `decision_log.json` 的关键要求

任务二中 `issue_resolutions` 必须存在且不能为空。每个问题都应形成：

```
found → diagnosis → fix → verify
```

例如：

```
{
  "issue_id": "I1",
  "phenomenon": "set_scan_chain 命令执行失败",
  "found": {
    "run_ref": "R1",
    "source": "runs/R1/R1.log",
    "excerpt": "unknown argument '-lenght'"
  },
  "diagnosis": {
    "located_object": "set_scan_chain 的 -lenght 参数",
    "root_cause": "参数拼写错误"
  },
  "attempts": [
    {
      "fix": {
        "action": "改为 -length",
        "artifact_ref": ["F1"]
      },
      "verify": {
        "run_ref": "R2",
        "resolved": true,
        "excerpt": "add_scan_chains completed"
      }
    }
  ]
}
```

如果问题属于 DFT 配置不符合任务要求，还必须填写 `violated_requirement`。如果修改了网表，`file_changes` 中必须包含：

- `type: "netlist"`；
- 网表 diff；
- LEC 报告引用 `lec_ref`。
