# 07. 工具执行、报告核验与 LEC

最后一层把前面的知识变成可审计的工程闭环。最重要的原则是：**工具退出码只说明程序结束，不说明链数、端口范围、Lockup、Wrapper、CTL 或 LEC 已满足任务。** 每个结论都要有正向证据。

## 1. 一次 Scan Insertion 运行应该经历什么

不同工具的命令名称会变化，但 Dofile 的逻辑顺序通常可以抽象为：

```text
加载 Liberty 与门级网表
        ↓
设置顶层与 DFT Signal
        ↓
配置 Internal Scan / Wrapper / 时钟与 Lockup
        ↓
执行 DRC
        ↓
预生成或检查 Scan Chain
        ↓
执行 Scan Insertion
        ↓
写出 Post-scan、CTL、SCANDEF 与报告
        ↓
逐项核验并归档本轮证据
```

赛题指南要求 Agent 处理加载、配置、DRC、链预生成、插入、报告和写出；若中途修改 Dofile，必须重新执行完整流程，而不是只补写一个报告。[赛题指南第 4.2.1～4.2.2 节](<../赛题二-基于大语言模型的Scan Insertion智能体系统设计.md>)

## 2. 先理解五类报告

| 报告 | 回答的问题 | 最小核验动作 |
| --- | --- | --- |
| Scan Signal | 工具实际认出了哪些时钟、复位、置位、SE、SI、SO？ | 对照任务书名称、极性、端口和域 |
| Scan Element | 哪些 DFF/LATCH 被识别或替换？ | 抽查单元类型和数量 |
| Scan Configuration | 哪些链数、边沿、域、Lockup 参数真正生效？ | 与 Dofile 和需求矩阵逐项比对 |
| Scan Chain / Cell | 链有几条、每条多长、单元顺序怎样？ | 与 SCANDEF、Post-scan 网表交叉比对 |
| Wrapper Configuration / Implementation | 哪些端口被包裹、模式和链怎样实现？ | 对照端口范围、Shared/Dedicated 和报告字段 |

报告之间要互相支持。若 Scan Configuration 说有 8 条链，而 Scan Chain 报告只有 4 条，应记录为配置不符，而不是选一份“看起来更好”的结果。[比赛入门文档 02：输出契约](<../比赛入门文档/02-任务边界与评分规则.md>)

## 3. Post-scan 网表抽查

报告是摘要，网表是最终事实。至少抽查以下内容：

1. 普通 DFF 是否被替换成 Liberty 中对应的 Scan Cell；
2. 每个 Scan Cell 的 `SI/SE/Q/CK` 是否接到预期网络；
3. 第一、最后一个单元是否连接 `scan_in/scan_out`；
4. Lockup 单元是否出现在要求的跨域/跨边沿位置；
5. Wrapper Cell 是否覆盖任务要求的端口，且没有误包 DFT 专用端口；
6. 测试模式下时钟、复位、置位和门控路径是否可控。

抽查不是只看单个实例，而是从端口沿链走一遍，确认“报告中的顺序”在实际连线中成立。SCANDEF 也必须与这条路径一致。[英文 DFT 教材第 2.7.3～2.7.4 节](<../../学习材料/DFT补强/VLSI Test Principles and Architectures - Design for Testability.md>)

## 4. 网表与 Liberty 的对象对齐

Liberty 是标准单元的“字典”：它描述单元名、引脚方向、逻辑功能和时序弧。工具若把网表中的 `DFF_X1` 误认成别的类型，后续 Scan Replacement、时钟识别和 DRC 都可能失真。因此应检查：

- 网表实例单元名在 Liberty 中确实存在；
- `D/Q/CK/RN/SN/SI/SE` 等引脚名称和方向一致；
- 同名单元的功能方程、时钟边沿和异步控制定义符合预期；
- Lockup、Wrapper、Scan Cell 的属性不是普通功能单元的误匹配。

遇到“工具不认识单元”时，先修复库/网表加载或映射问题，再讨论 DFT 规则；不要通过删除实例或屏蔽报告掩盖对象对齐失败。[赛题指南输入与受保护文件说明](<../赛题二-基于大语言模型的Scan Insertion智能体系统设计.md>)

## 5. Yosys EQY 与 LEC 的最小知识

LEC（Logic Equivalence Checking，逻辑等价检查）回答的是：“修改前后，给定相同输入和时序假设，两个网表的功能是否一致？”本赛题任务二在修改 Pre-scan 网表后要求用 Yosys EQY 比较原始与修改后的网表。[比赛入门文档 00：EQY 说明](<../比赛入门文档/00-快速上手.md>)

理解 EQY 时抓住这些对象：

- **Gold**：参考设计，通常是原始网表；
- **Gate**：待验证设计，通常是修改后的网表；
- **顶层模块**：两个设计必须能对应到同一功能边界；
- **库模型**：黑盒或标准单元需要一致的模型/映射；
- **失败报告**：区分环境/建模失败与真正的功能不等价。

EQY 报告失败不一定表示逻辑改坏了，也可能是顶层、参数、黑盒或库模型没有对齐；但在没有解释并修复环境问题前，不能把失败写成“等价通过”。成功也只证明比较的那两个输入在给定假设下等价，不证明 Scan Insertion 的链、Wrapper 或报告满足题目。[EQY 官方文档](https://yosyshq.readthedocs.io/projects/eqy/en/latest/)

## 6. 三类结果要分开写

| 结论 | 含义 | 后续动作 |
| --- | --- | --- |
| 通过 | 工具流程完成，且需求矩阵中的证据全部满足 | 归档 final run |
| 失败 | 有明确违规或 LEC 不等价 | 保留原始日志，做最小修复并完整复跑 |
| 证据不足 | 工具退出正常，但缺报告、字段无法解析或网表未抽查 | 不得交付为成功，补跑/补证据 |

“证据不足”是很重要的第三种状态。它避免团队把空报告、旧轮次报告或静态推测当成最终事实。[比赛入门文档 03：工具成功与需求核验](<../比赛入门文档/03-技术路线与系统拆解.md>)

## 7. 最小修复与复跑纪律

当发现问题时，遵循以下顺序：

1. 用日志和报告锁定具体对象；
2. 判断是 Dofile/约束、工具环境，还是允许修改的 Pre-scan 网表；
3. 只做能解释根因的最小修改；
4. 保存 `R1/R2/...` 每一轮完整日志和产物；
5. 重新执行 DRC、建链、插链、写出和报告核验；
6. 任务二修改网表时，再运行 EQY 并保存 Gold/Gate 配置和失败/通过报告；
7. 只有最终轮次全部满足需求，才复制到 `final_results/`。

禁止用 Ignore、降低检查级别、删除违规对象或手工伪造报告来“修复”结果；赛题指南把这些行为列为不合规。[赛题指南第 8 章行为边界](<../赛题二-基于大语言模型的Scan Insertion智能体系统设计.md>)

## 8. 一页验收清单

- [ ] 输入的 Liberty、Pre-scan 网表和顶层与任务说明一致；
- [ ] DFT Signal 的名称、极性、时钟边沿和域有报告证据；
- [ ] Scan Element 数量/类型与网表抽查一致；
- [ ] Internal/Wrapper Chain 数量、长度和范围满足要求；
- [ ] Lockup、门控/派生时钟、复位/置位问题有明确结论；
- [ ] Post-scan、CTL、SCANDEF 和所有要求的报告均已生成且可解析；
- [ ] 多轮运行只采用真正满足需求的最终轮次；
- [ ] 若修改网表，EQY LEC 对 Gold/Gate、顶层、库模型和黑盒设置均有记录；
- [ ] 最终结论能从需求→配置→日志→报告→网表/LEC 逐条回溯。
