# 规则索引与证据使用报告

本报告配合 [[../../../docs/DFT与规则学习/案例学习/案例具体分析/01-规则索引与证据使用|规则索引与证据使用]] 使用。内容重点不是某一条 DFT 命令，而是“遇到现象以后，怎样找到正确的检查方向”。

## 1. 概述：为什么需要索引

规则卡是一套较大的维修手册，规则索引负责目录和初步分诊。

假设报告里出现“时钟不可控”。这句话并不能直接决定应该修改哪一行。原因可能是扫描时钟端口写错、ICG 没有接扫描使能、时钟经过了工具无法自动识别的 latch，或者多级门控时钟的初始化周期不够。

如果一看到同一个错误编号就套同一个修复，Agent 很容易把真正的问题越修越坏。所以索引先按现象把问题分流，再打开对应的完整规则卡。

## 2. 这份索引覆盖什么

索引连接了 51 张卡片：任务一的 21 张要求检查卡，加上任务二的 30 张官方预置问题卡。

任务一没有官方的 original/preset 故障清单，所以它的卡片使用 `REQ-*` 编号，意思是“需要检查的要求”。任务二有官方 `ISSUE-01` 到 `ISSUE-06`，所以保留官方编号。

这个区别很重要。`REQ-01` 不是说 Public 已经观察到一个失败；它说的是，运行时必须检查这一条要求。任务二的 `ISSUE-01` 则来自官方提供的预置问题描述，但它也仍然需要在真实工具运行时重新验证。

## 3. 一张规则卡怎样读

可以把一张卡读成一条完整的侦探链：

1. `problem_pattern` 说要找哪一类问题；
2. `observable` 说报告、日志或网表里能看到什么；
3. `recognition` 说怎样区分相似现象；
4. `root_cause` 说在证据充分后可以作出什么判断；
5. `standard_fix` 说官方材料支持的正常修复方向；
6. `equivalent_fix` 说官方明确承认的其他等效写法；
7. `forbidden_fix` 说哪些做法只是把错误藏起来；
8. `verification` 说修复后必须重新检查什么。

诊断逻辑可以概括为：先记录现象，再确认连接和配置，最后用修复后的结果复查。看到扫描链没有建立，只说明结果异常；还要区分是网表没有加载、时钟声明错误、门控时钟没有打开，还是链数配置不符合任务。

## 4. 为什么 source_case 不能触发规则

`source_case` 只是来源标签。例如某个规则来自 T2C1，并不意味着以后看到 T2C1 的端口名就应该自动套用它。

真正应该触发规则的是证据组合：错误命令、对象类型、网表连接、任务书约束和报告结果。端口名、实例路径和数量只属于当前案例绑定，不能直接升级成 Hidden case 的通用条件。

这也是为什么规则卡把“通用模式”和“案例绑定”分开。通用部分讲“扫描时钟声明错误”这一类问题；案例绑定部分才写 `clk`、`wb_clk_i` 或某个具体实例。

## 5. 相同现象为什么不能直接套同一修复

以 DFTR1 为例。Public 材料中它可能分别对应：

- 把 reset 端口错当成扫描时钟；
- 时钟端口名称不存在，导致声明失败；
- 级联 ICG 的初始化周期不足；
- latch 输出时钟没有与主时钟建立关联。

它们的共同表面现象是“某些 FF 的时钟不可控”，但证据位置不同，修复方法也不同。索引要求先看失败命令、违例对象聚集位置和时钟路径，再选卡片。

同样，`Ignore` 也不能一概而论。有些 case 明确允许忽略 TIE 类规则，有些 case 要求 DRC 清零；某些 case 可以排除时钟传输 latch 或 JTAG TAP，但不能用排除功能 FF 的方式换取“零违例”。

## 6. 实际使用流程

拿到一个新 case 时，可以按下面五句话走：

“当前任务做的是前置处理还是完整插链？”

“这个现象是命令没有成功，还是命令成功后结果不符合任务？”

“能否在日志、报告或网表中指出对应证据？”

“这个修复是解决原因，还是只是把报告隐藏起来？”

“修完以后，哪一份报告或网表能证明它真的好了？”

如果第五句答不出来，说明修复还没有闭环。

## 7. 收尾

规则索引的价值不是让读者背更多错误码，而是让诊断从“看到一个词就猜答案”变成“看到证据再选择规则”。它把 DFT 工程师的判断过程拆成了可复核的步骤：先分类，再定位，再修复，最后验证。
