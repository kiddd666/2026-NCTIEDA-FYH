# Public 数据集地图与运行契约报告

本报告配合 [[../../../docs/DFT与规则学习/案例学习/案例具体分析/00-Public数据集地图与运行契约|Public 数据集地图与运行契约]] 使用，帮助刚开始阅读 DFT 和 Scan Insertion 材料的研究生建立整体认识。

## 1. 概述

先建立一个简化模型：芯片由逻辑单元、寄存器、时钟和控制信号组成。Scan Insertion 是在这个已有设计上增加测试结构，使测试设备能够把数据移入寄存器，再把内部状态移出。后续的 DRC、扫描链和网表报告，都是在检查这套测试结构是否按要求建立。

这张表不负责讲某一条命令，而是先回答三个问题：Public 数据集中有哪些案例？每个案例允许工具运行多久、最后必须交什么？后续看到一份新任务时，怎样确定检查范围。

## 2. 这张地图记录了什么

Public 数据集一共有 11 个案例：任务一 6 个，任务二 5 个。任务一主要训练“怎样按照任务书完成扫描插入”；任务二主要训练“原来的 Dofile 有问题时，怎样根据现象定位并修复”。

这两类任务看起来都叫 Scan Insertion，但工作重点不同。任务一更像按照施工图建一套检查通道，任务二更像拿着故障报告修一套已经写坏的施工方案。

表中的每一行都是一个独立契约。它至少包含四类信息：

1. 要处理什么设计、使用什么网表和库；
2. 任务的终点是前置处理，还是完整插链；
3. 允许的 wall time，也就是整个案例最多运行多久；
4. 最后必须交哪些网表、报告、日志和决策记录。

这里的“契约”可以理解为验收单。它不是建议，而是说明“做什么才算完成”。

## 3. 为什么不能只看 DRC 是否为零

一个常见的误读是：只要报告里写着零个 DRC 违例，就说明任务完成了。

实际上，DRC 只回答“工具发现的规则问题是否清掉”。它不回答下面这些问题：

- 扫描链是不是规定的数量；
- 每条链是不是没有超过长度上限；
- 不同的时钟域有没有被错误地串到一起；
- 应该排除的 JTAG 或独立时钟域有没有误入扫描链；
- 输出的 CTL、SCANDEF 和最终网表是否与报告一致；
- 任务要求的日志和决策记录是否完整。

所以地图把“基本功能”“例外规则”“输出文件”放在同一个契约里。它提醒执行者，零 DRC 只是验收的一项，不是全部验收。

## 4. 六个任务一案例怎样理解

任务一的前两个案例是入门边界：T1C1 和 T1C4 只做 ICG 重连、DFF/SFF 替换或回替，不建扫描链。它们的最终证据主要是几个阶段网表，而不是扫描链报告。

T1C2 是按功能区域划分扫描分区的案例。它要求不同 FIFO、串行接口、寄存器和控制逻辑使用不同的分区、链数和扫描使能。

T1C3 加入了黑盒 AES 模块和 CTL。这里的难点是：黑盒内部电路不可见，必须依靠 Liberty 模型和 CTL 文件把它的扫描结构接入顶层。

T1C5 是大型多时钟设计。它要求把一些门控时钟声明成 pseudo PI，告诉工具“这些内部时钟虽然不是顶层输入，但要按独立测试时钟处理”。

T1C6 关注 wrapper 和长移位寄存器。它要求保留已有扫描段，并针对不同端口选择 none、dedicated 或 shared wrapper。

任务二的五个案例则是在这些能力上加入故障：例如没有加载网表、扫描时钟端口写错、复位极性写反、分区绑定错误、链长和端口命名不符合要求。

## 5. wall time 应该怎样理解

表里的 150 秒、300 秒、4800 秒或 3600 秒，指整个 case 的 wall time 上限。它不是“每条命令都能运行这么久”，也不是工具内部自动重试次数。

因此 Agent 需要在开始前先确认：输入文件在哪里、设计顶层是谁、工具脚本怎样输出结果，再在一个预算内完成运行、检查和交付。如果大型 case 只剩很少时间，不能把时间全部花在反复试错上，却没有留下报告和日志。

## 6. 输出契约怎样读

输出清单可以分成三层：

- 最终设计结果：例如 `post_scan.v`、`post_replace_unscan.v`；
- 工具解释结果：例如 DRC、scan chain、scan signal、scan partition、wrapper 报告；
- 过程证据：每轮完整日志、Agent 执行摘要和决策记录。

第一层说明“最后生成了什么”，第二层说明“工具认为它是什么”，第三层说明“它是怎样生成的”。只有三层互相对得上，结果才容易复核。

## 7. 收尾

核心结论是：先把 Public case 当成一份验收合同来读，不要急着抄 Dofile。先确认任务终点、运行预算和输出契约，再决定需要哪些配置和报告。

这张地图的作用，是让后面的规则卡有一个坐标系。规则卡说明怎样判断问题；这张地图说明应在什么任务、什么边界和什么交付要求下判断。
